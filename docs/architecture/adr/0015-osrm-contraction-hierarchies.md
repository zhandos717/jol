# 0015. OSRM на Contraction Hierarchies вместо MLD

**Контекст.** В лёгком профиле OSRM — самый крупный потребитель памяти. MLD хранит веса по ячейкам (`cell_metrics`, 187 МБ), нужные для быстрого пересчёта весов под пробки. Пробок у нас нет.

**Замер.** OSRM отдельно, `--mmap`, одинаковые случайные маршруты, лимит памяти контейнера:

| Лимит | MLD: цена / карта / межгород, req/s | CH: цена / карта / межгород, req/s |
|---|---|---|
| 512 МБ | 445 / 672 / 110 | — |
| 320 МБ | 433 / 697 / 108 | — |
| 256 МБ | 438 / **27** / **19** — вытеснение кэша | 424 / 324 / 78 |
| 128 МБ | — | 445 / 778 / 111 |
| 112 МБ | — | 443 / 784 / 111 |
| 96 МБ | — | 435 / **14** / **5** — вытеснение кэша |

CH держит полную скорость примерно со 112 МБ; MLD нужно около 320 МБ.

**В составе лёгкого стека** (все сервисы под нагрузкой 2000 водителей) при лимите 160 МБ расчёт цены упирался в таймаут 3 с — запас нужен под соседей. При 256 МБ: 399 req/s без ошибок, сумма пиков стека 213 МБ.

**Решение.** Оба профиля на CH (`osrm-contract`), лимит OSRM в лёгком профиле — 256 МБ.

**Цена.**
- Подготовка дольше: ~14 мин и ~1 ГБ на 1 vCPU против ~2 мин и 725 МБ у MLD. Один раз на обновление карты.
- Нельзя быстро пересчитывать веса под пробки. Понадобится — вернуть MLD рядом (оба набора файлов уживаются в одном томе).

**Замечание о методике.** `docker stats` плохо видит файловый кэш при mmap, поэтому мерилом служит не «сколько показывает», а «при каком лимите скорость не падает». Шум одной машины заметен; выводы сделаны по повторным прогонам.
