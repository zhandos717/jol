# 0001. Микросервисы в монорепозитории

**Контекст.** Первая версия — один файл на Node.js на 650 строк. Домены (учёт водителей, цена, раздача заказов, межгород, доставка событий) развиваются с разной скоростью и нагрузкой: координаты приходят тысячами в секунду, а профили меняются раз в неделю. Команда маленькая.

**Решение.** Шесть сервисов по границам доменов (bounded contexts): `accounts`, `fleet`, `pricing`, `dispatch`, `intercity`, `realtime`. Один репозиторий на npm workspaces и TypeScript project references; общие пакеты `@jol/contracts` (схемы и типы) и `@jol/kit` (инфраструктура). Один Dockerfile на все сервисы.

**Альтернативы.**
- *Модульный монолит.* Дешевле в эксплуатации, честнее для команды из 2–3 человек. Отвергнут, потому что цель проекта — показать независимое масштабирование горячих путей (`fleet`, `realtime`) и изоляцию отказов.
- *Репозиторий на сервис.* Сложнее менять контракт атомарно. Для одной команды монорепо проще.

**Последствия.**
- Изменение контракта — один коммит, а компилятор находит всех потребителей.
- Появляется распределённая согласованность: учёт в `accounts` отстаёт от `dispatch` на десятки миллисекунд. Это видно в UI только как задержка счётчика заработка.
- Цена эксплуатации выше: 6 процессов вместо одного. Компенсируется общим `kit` (единый старт, логи, здоровье, остановка).
