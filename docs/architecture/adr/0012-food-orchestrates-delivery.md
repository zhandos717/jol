# 0012. Еда заказывает курьера у dispatch: оркестрация с запасным планом

**Контекст.** Доставка еды состоит из двух процессов разной природы: кухня (принять, приготовить, упаковать) и курьер (найти, забрать, вручить). Курьерская часть уже решена в `dispatch` для посылок: раздача, код вручения, отслеживание.

**Решение.** Сервис `food` владеет заказом еды и **оркестрирует** доставку:
1. Ресторан принимает заказ → `food` вызывает RPC `dispatch.delivery.request`. Ключ идемпотентности — `courier_request_id`, сохранённый в заказе ещё до вызова. Повтор после таймаута вернёт ту же доставку, а не закажет второго курьера.
2. Если вызов не удался (`dispatch` недоступен), заказ остаётся в `cooking` без курьера, и фоновая задача повторяет бронирование каждые 10 с.
3. `food` слушает события `jol.dispatch.order.*` с `source = food` и переводит свой заказ: курьер назначен → в пути → доставлен.
4. **Запасной план.** Если велокурьер не найден за 90 с (`order.cancelled`, `no_drivers`), `food` заводит новую попытку с новым ключом и тарифом «на авто». После второй неудачи заказ отменяется с причиной `no_courier`.

Заказы с `source = food` не занимают слот «один активный заказ на пассажира», поэтому клиент, ждущий еду, может вызвать такси.

**Альтернативы.**
- *Хореография* — `dispatch` сам слушает `food.order.accepted` и создаёт доставку. Меньше связности, но логика запасного плана размазывается по двум сервисам, и её сложнее увидеть и протестировать.
- *Отдельный курьерский сервис.* Дублировал бы раздачу из `dispatch`: тот же поиск ближайшего, офферы, таймауты.

**Последствия.** Курьер заказывается при принятии заказа, а не по готовности, поэтому приезжает примерно к концу готовки. Сага проверена вживую: велокурьер не найден, через 91 с предложение получил курьер на машине, заказ доставлен (`courier_attempts = 2`).
