# 0014. Лёгкий профиль: те же сервисы в одном процессе

**Контекст.** Полный профиль занимает ~840 МБ памяти, из них 67% — OSRM с графом дорог Казахстана целиком в памяти, ещё 27% — семь процессов Node.js по 25–50 МБ. Для демо и пилота нужен VPS на 1 ГБ.

Переписывание на Go сэкономило бы около 150 МБ (18%) ценой переписывания бэкенда; основной потребитель, OSRM, уже на C++. Открытые аналоги на Spring Cloud или с полным набором инфраструктуры (Eureka, Kafka, Elastic, Jaeger) требуют 4–8 ГБ.

**Решение.** Второй профиль развёртывания поверх того же кода (`docker-compose.lite.yml`, `make up-lite`):
- **Один процесс Node.js.** Сервис — это значение (`defineService`), а не процесс. `all-in-one` запускает все семь определений через `runServices`, каждое со своим портом, своей ролью в БД и своим подключением к NATS. Границы остаются прежними: общение только через события и RPC в NATS, схемы БД раздельные.
- **OSRM с `--mmap`.** Граф читается с диска по требованию; в памяти остаётся рабочий набор.
- **PostgreSQL для маленького сервера:** `shared_buffers=16MB`, `max_connections=30`, пул по 3 соединения на сервис.
- **Жёсткие лимиты памяти** на контейнеры: заявленный объём проверяется, а не оценивается.
- **Один шаблон конфигурации nginx** для обоих профилей: адреса сервисов подставляются из окружения.

**Замер** на 1 vCPU, 2000 водителей онлайн (`make bench`):

| | Полный профиль | Лёгкий профиль |
|---|---|---|
| Память в покое | ~840 МБ | ~80 МБ |
| Пик под нагрузкой | — | **219 МБ** |
| Координаты водителя | ~5 300 req/s | ~5 500 req/s |
| Расчёт цены с маршрутом | ~750 req/s | ~585 req/s |

**Где ловушка.** Лимит памяти контейнера учитывает и файловый кэш. С `--mmap` при лимите 160 МБ граф постоянно вытеснялся: 19 req/s и p50 2.6 с. При 256 МБ городской рабочий набор остаётся в кэше: ~370–585 req/s и p50 50–80 мс.

**Альтернативы.** Valhalla вместо OSRM — тайловая и экономная по памяти, но медленнее на массовых запросах и требует своей подготовки данных. Только карта Алматы — ещё ×10 по OSRM, но ломает межгород.

**Последствия.**
- В лёгком профиле сервисы нельзя масштабировать по отдельности, и падение одного процесса роняет все семь. Для пилота это приемлемо, переход на полный профиль не требует изменений кода.
- Подготовка карты по-прежнему требует ~1 ГБ на несколько минут один раз (`make map`); её можно выполнить на другой машине и перенести том.
